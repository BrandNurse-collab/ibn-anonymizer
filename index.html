How the Anonymizer protects your data

The tool removes or replaces the fields that identify a person, keeps the fields you need for analysis, and checks the result for anything that slipped through.

The six steps

  1. Upload an Excel or CSV claims file. It is read inside this browser tab.
  2. Detect which columns hold names, enrollee IDs, ages, contact details and clinical or financial data. You can correct any column.
  3. Configure what to remove, how anonymous IDs are built, the age bands, and optional diagnosis standardisation.
  4. Preview a before-and-after sample and review data-quality warnings.
  5. Protect the full file, then review any residual identifiers the scanner finds, for example a name typed into a remarks column.
  6. Download the anonymized Excel or CSV file and a processing report.

Pseudonymization, not irreversible anonymization

Enrollee IDs are replaced with consistent anonymous IDs so repeat claims stay linked. Because the same organization key always produces the same anonymous ID for the same enrollee, this is technically pseudonymization. Anyone who holds both the key and the original enrollee list could re-link records. Keep the key with the team that already holds the source data, and share only the anonymized output.

Technical method: HMAC-SHA-256 keyed with your organization privacy key, truncated to 40 bits and written in Crockford base-32. Family IDs and member IDs use separate key domains.

How family grouping works

Many HMOs number members as 12345/0, 12345/1, 12345/2. The part before the last slash is treated as a possible family. The number after the slash is kept only as a position (-M0, -M1) and is never used to guess the relationship. Relationship comes only from your Relationship column, exactly as submitted.

What still carries some risk

Removing names and IDs does not remove every route to re-identification. A rare diagnosis combined with an age band, a small provider and a service date can point to one person in a small scheme. Before sharing outside your organization, consider:

  • Wider age bands for small schemes.
  • Removing free-text columns you do not need.
  • Reporting rare conditions at an aggregated level rather than line by line.

Data cleaning & standardization

Cleaning adds new columns and never overwrites a source value. Diagnosis text and ICD-10 codes are matched against local reference dictionaries and reduced to a short clinical term such as Hypertension or Respiratory Infection. When a field lists several diagnoses, the first one the dictionary recognises is used and the row is marked “Mapped – First Diagnosis”. Anything the dictionaries can't match confidently is marked UNMAPPED – REVIEW or REVIEW REQUIRED rather than guessed, and you can correct it on the Review step.

Medicines are mapped to their generic name only when the generic appears in the description or the brand is in the reference list. Unfamiliar brands are left for review. Provider names are tidied for spacing and capitalisation; different providers are never merged automatically.

You can clean before anonymizing (so the anonymized file carries cleaned fields), after anonymizing (cleaning reads only the protected data), or on its own. A clean-only export still contains identifiers.

What never leaves your browser

The source file, the organization privacy key and the link between original and anonymous IDs. The link exists only in memory while the file is processed and is discarded when processing finishes. It is never written to the export or the processing report.

Wording we use deliberately

Your uploaded data is processed securely in your browser and is not sent to an AI model for routine anonymization or data cleaning. The tool is designed with privacy-first data processing principles. It does not certify compliance with the NDPA, GDPR or any other law. Whether a given output is adequately de-identified for a particular use is a judgement for your data protection officer.

Organization privacy key
